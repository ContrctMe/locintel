01

The organizing idea: three gates

Entitlements, permissions, and hierarchy scope are three different questions that fail in three different ways. Conflating them is the most common way this class of application rots. Every request passes all three, in order, and the pipeline returns a decision plus a reason — which is also exactly what the audit log needs to record.

01

Entitlement

Does this organization’s plan include the capability at all?

Subject · organization
→ 402 & upsell, not an error
02

Grant

Does this principal hold this right on this domain?

Subject · user
→ 403, a real denial
03

Scope

Over which nodes of the hierarchy does that grant apply?

Subject · user × subtree
→ filter, never an error

The scope gate is why the authorization port needs two operations rather than one. Nearly every pluggable authorization abstraction ships can(principal, action, resource) and stops there — sufficient for detail endpoints, useless for lists. Add scopeFor(principal, action) returning a set-valued NodeScope, resolved to materialized path prefixes so a regional manager covering three thousand sites stays a prefix match rather than an id list. Make repository methods require a scope argument, and “forgot to filter by location” stops being expressible.

03

Consequences not explicitly chosen

Decisions combine into constraints that hold whether or not anyone decides them.

Path stamps must be tree-keyed, not a single column

From 02 + 04. Facts stamp an ancestor path, and hierarchy_id exists for future trees. If the stamp is one path column, adding a second tree means backfilling every fact table. Make it a child table or JSONB keyed by hierarchy from the start — near-zero cost now, a large migration later.

Guests need sessions

From 07 + 21. “No anonymous actions” plus cookie-based sessions means guests get a session cookie too — without one there is no CSRF token and no rate-limit subject. Session issuance therefore happens before authentication, and the principal pipeline builds a tenant-scoped guest from the request host.

Wolverine is three subsystems at once

From 13 + 17 + 23. It is simultaneously the mediator for slice handlers, the bus carrying integration events across module boundaries, and the outbox fanning out audit. That consolidation is the reason to choose it — and also a concentration of risk, since a problem in it is a handler problem, a messaging problem, and an audit problem at the same time.

Audit interceptors register on every module’s DbContext

From 12 + 17. Row-level diffs are captured per module but written into the audit module’s schema. One database keeps that inside a single transaction — which is precisely why one database beat database-per-module.

The occurrence projection needs explicit rebuild triggers

From 26 + 27 + 28. Rule edits, exception changes, and the rolling horizon all invalidate materialized occurrences — and so does a change to a site’s timezone. That last one is the case that gets forgotten, and it shifts every published opening hour silently.

Metering needs append-then-rollup

From 08 + 09. A single counter row per org per period is a contention hotspot under concurrency. Append usage events, roll up periodically, and keep an approximate live counter for enforcement — the Grace policy absorbs the imprecision.

Email sits inside the authentication path

From 07 + 32. Magic links deliver the identified-contact tier, so a transactional email outage is a partial authentication outage. That argues for a documented fallback transport, or at minimum an explicit degradation story rather than a silent one.

Audit configuration is self-referential

From 12. Because audit policy is configurable per org, changes to that policy must themselves be audited, and a platform floor has to exist that no tenant can configure below.

04

Carried forward

Residency is regional silos today and full multi-region routing later (decision 35). These six rules have to hold from the first commit, or that later step stops being an addition and becomes a rewrite.

No ambient connection string

Every data access resolves its context from the org’s region, even while that resolution always returns the same connection. This is the single biggest lever — retrofitting it later touches the lowest layer of everything.

Region resolves outside the regional database

Org-to-region has to be answerable before a connection opens, so it cannot live in the database being connected to. Resolve it at the edge from the subdomain or custom domain, or from a small global directory replicated to every silo.

UUIDv7 keys, never database sequences

Identifiers must be globally unique so nothing collides when regions are later routed as one logical product. UUIDv7 keeps index locality without giving up that property.

Object storage carries region in buckets and keys

From the first upload, not the first migration. Storage keys are referenced from durable rows and rewriting them later means touching every reference.

Cache keys carry region alongside org

Decision 05 already established that org is never ambient in a cache key. Extend the same convention to region now, while there is only one value it can take.

Identity is global, org data is regional

WorkOS spans regions while tenant data does not. Making that split explicit now avoids discovering mid-migration that user records were assumed to live beside the org rows that reference them.

05

Build sequence

The first three steps are where a wrong call is expensive. Everything after is additive.

01
Foundations
Postgres with RLS, module skeleton, DbContext per schema, Wolverine wired for mediation, messaging, and the outbox. UUIDv7 keys and a region-resolved context factory from the first commit. Deletion tiers, the Aspire AppHost, architecture tests, and the tenant-isolation golden suite: replay every endpoint as tenant B against tenant A’s identifiers and assert 404 across the board.
02
Identity
OIDC seam, WorkOS adapter, cookie session, the three principal tiers, and the organization switcher — plus the notification transport, since magic-link delivery is what makes the identified-contact tier real. Layered rate limiting lands here, because the guest tier arrives with it.
03
Hierarchy, sites, and time
Nodes, sites, ltree paths, and the scope resolver providing both can and scopeFor. The temporal model ships with it — site timezone, wall-clock rules, business-date stamping, RRULE schedules, and the occurrence projection with its rebuild triggers.
04
The gates
Entitlements across all four shapes with their limit policies and downgrade preflight; append-then-rollup metering; roles, grants, and time-boxed exceptions.
05
Audit
Per-org policy resolution, the transactional write path with outbox fan-out, and the async read-access path on its own partitioned store.
06
Storage and ingest
Presign tickets, quarantine and scanning, derivatives, retention and erasure. Then KMS-wrapped connector credentials, the staging, dry-run and upsert core, file upload, the first pull connector, and the idempotency layer the push path depends on.
07
Management console
The first real vertical slice, exercising all three gates, ingest, storage, and audit end to end — and the module generator that makes the second slice cheap.
